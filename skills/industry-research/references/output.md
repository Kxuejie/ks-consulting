# 报告结构与输出

## 共用底稿

默认结构如下，研究正文遵循 SKILL.md 的固定骨架和 framework.md 的详细方法。可调整小节篇幅与行业副标题，默认保持 S1—D2 七个板块可分别定位，D3 按需加入；用户明确限定范围时记录取舍。输出格式不改变研究覆盖要求。

1. 封面与研究摘要：行业、地区、研究截止时间、用途、核心判断。
2. 研究边界与三维画布：产品/服务定义、统计口径、三维问题和摘要。
3. 空间：流程与产业链、各环节参与方、价值流动与话语权、阶段判断。
4. 时间：规模与公式、历史变化与驱动、周期、PEST、条件情景、阶段判断。
5. 深度：重点环节选择、竞争格局、商业模式与利润机制、成功关键因素；按需追加单一公司。
6. 综合洞察与启示：跨维度推导、受益/承压类型、适用条件、跟踪指标。
7. 来源与研究限制：来源全称、统计/发布日期、URL或资料页码、影响判断的数据缺口。
8. 行业术语解释：报告最后一章，解释正文中的专有词、技术名词与指标，包含通俗定义、行业作用、例子或区别及必要口径。

按 [论证与表达](reasoning-and-writing.md) 执行“小节/图表观点 → 事实依据 → 通俗机制 → 影响及边界”。一级框架标题保留，紧接一句判断；小节标题或首句同样给出具体观点。长论证用段落，不能为卡片整齐而删成结论短语；表格用于有相同字段的比较。正文首次出现的重要术语就地解释，文末词汇章供复习查阅。

## HTML

读取并填充 `../assets/industry-report-template.html`，单文件 UTF-8，可本地打开，无外部字体、脚本和样式依赖。模板源自现有 Case 报告，已换为行业报告章节。

- 替换模板中的所有 `{{...}}`；纯文本字段转义 HTML，正文槽插入由底稿生成的语义化 HTML。
- 将 Markdown 段落、表格和来源完整转换，保持编号与来源一致。
- 产业链可用 `.flow` 与 `.flow-step`，三维画布可用 `.framework`、`.beam` 和 `.rooms`；HTML流程图在Word中提供等价可编辑表格或带文字说明的图。
- 每个维度以 `.stage-conclusion` 收束。正文事实、推算、假设使用明确文字标签，不仅靠颜色。
- `SPACE_TAKEAWAY`、`TIME_TAKEAWAY`、`DEPTH_TAKEAWAY` 分别填入维度的一句前置判断；正文槽保留小节观点、证据和完整解释。图表前先给数据解读，不能只有大数字卡和行业标签。
- 最后填充 `GLOSSARY_HTML`，保留 `#glossary` 目录入口。词条采用可阅读的定义列表或卡片，不把术语解释压成缩写对照表。
- 保留深墨侧边目录、暖米纸张、蓝紫层级、衬线标题、打印及回顶按钮；不带 Case 的学员评价、答案校验或题型标签。
- 来源使用可点击链接，引用就近放置；本地资料使用文件名与页码，让外部读者理解出处。
- 验证所有目录锚点有目标、无残留占位符，至少检查桌面和约390px手机视口。宽表格只在自身容器滚动，不能撑宽整个页面。
- 检查打印视图表格可换行、无裁切，长章节能自然分页；超宽表格按业务含义拆分为列数较少的表格。

## Word

Word 是可编辑的 `.docx` 长报告。保留共用底稿的所有论证、首次术语解释及来源，重新组织为正文、标题和表格，不把网页截图插成整份报告。每个主要板块标题下先放一句判断，事实与解释随后展开；最后保留“行业术语解释”章，使用二级词条标题与自然段。

采用 Word 原生标题样式、自动页码、清晰的段落间距与连续页式布局。正文约11pt，中文字体显式指定。标题黑色，表格浅色表头、浅灰边框、跨页重复表头，避免长行固定高度。默认 Letter 纵向；用户指定A4或提供版式时遵循其要求。

### 随附构建脚本

`scripts/build_word.py` 接受由统一底稿整理的 UTF-8 JSON，依赖 `python-docx`。在 Codex 桌面先调用工作区依赖工具定位 Python；其他环境使用有该依赖的 Python。所有字符串为纯文本，脚本不解释 Markdown；来源链接使用下述 links 类型。

```json
{
  "title": "某行业研究报告",
  "subtitle": "研究地区及资料截止日期",
  "summary": "核心判断及最重要的成立条件",
  "sections": [
    {
      "title": "空间 行业全景图",
      "blocks": [
        {"type": "heading", "text": "流程与参与方", "level": 2},
        {"type": "paragraph", "text": "带有来源编号的完整正文 [1]。"},
        {"type": "bullets", "items": ["第一点", "第二点"]},
        {"type": "table", "headers": ["环节", "价值与证据"], "rows": [["投入", "说明及来源"]], "widths": [1, 3]},
        {"type": "links", "items": [{"text": "[1] 机构 报告名称 日期", "url": "https://example.com/report"}]}
      ]
    },
    {
      "title": "行业术语解释",
      "blocks": [
        {"type": "heading", "text": "本行业的重要术语", "level": 2},
        {"type": "paragraph", "text": "写明准确而通俗的定义、在行业中的作用、帮助理解的例子或区别及必要限制。"}
      ]
    }
  ]
}
```

`paragraph` 支持普通文本公式；复杂数学式或特殊图表按需用文档工具补充。脚本支持的块为 heading、paragraph、bullets、table、links；需要超出这些块的形式时用文档工具实现，不让脚本静默丢内容。

```text
python scripts/build_word.py report.json report.docx
```

上面的 JSON 仅演示数据格式，实际生成必须包含所需的全部研究章节与真实词条，最后一个 section 为“行业术语解释”。脚本只检查数据结构，不自动判断研究论证是否充分，也不自动补词汇章，执行者须按框架与表达验收。

默认拒绝覆盖输出；只有有意更新该文件时才使用 `--overwrite`。JSON 是可选的格式转换中间件，研究底稿仍为 Markdown；两者必须核对，尤其是表格、公式、脚注和条件假设。长报告可增加目录，但交付前须确认页码已更新；随附脚本依靠原生标题提供导航，不写入未经更新的目录页码。

### 排版验收

运行可用的文档渲染器并检查全部页图，关注中文缺字、表格裁切、孤立标题、大块留白和来源链接。可使用当前环境 documents skill 的 `render_docx.py`。若缺少渲染引擎，仍可检查 DOCX结构、文字与链接，但须明确未完成视觉验收，不宣称已验证最终分页。

## 双格式一致性

先使用底稿的 S1—D3 核对表逐项定位到输出报告，确认完整论证与限制说明没有在转换中丢失，再抽查摘要、规模数字、周期判断、重点环节、公式、表格行数及来源，确保 HTML 与 Word 对应底稿。发生修改时先改底稿，再同步输出。正文末尾的资料限制属于研究内容；内部框架核对表、开发过程、脚本日志和内部测试结果不进入报告。
